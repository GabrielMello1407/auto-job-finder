# auto-job-finder

Job-application agent for anyone, in any field (TypeScript, Node 22.12+). CLI entry: `npm run ajf -- <command>`, or `ajf <command>` after `npm link` (see README). Code identifiers are in English. The local UI is in English and Brazilian Portuguese (see UX). CLI messages, task logs and the files generated for the user are in Brazilian Portuguese for now; what recruiters read follows the language of each job. The main docs are in English with a Brazilian Portuguese copy next to each one (see Docs).

## LLM providers

`src/providers/`, detected in `providers/index.ts#detectProviders`:
- Subscription CLIs, preferred: `claude-code` (`claude -p --json-schema`), `codex` (`codex exec --output-schema`), `gemini-cli` (`gemini -p -o json` plus JSON validated by Zod).
- APIs: `anthropic`, `bedrock` and `vertex` (official SDKs, same code path), `openai` (Responses API, or Chat Completions when `OPENAI_BASE_URL` is set), `gemini` (REST).

`AJF_PROVIDER` forces one. Every LLM call goes through `src/llm.ts`, which keeps the providers interchangeable. When you add a provider, implement `LlmProvider` and register it in `PROVIDERS` and `createProvider`. Calls can carry images (`CallOptions.images`, `src/providers/images.ts`): APIs send them in the request body, `codex exec` uses `--image`, Claude Code and Gemini CLI get a copy in the isolated folder and open it with their file-reading tool; every provider must handle them.

## User data

- Per-person data lives under `AJF_HOME` (default: the repo root) in `profile/`, `data/` and `output/`.
- All three are gitignored. Never commit personal data.
- `ajf init` and the UI wizard (`src/onboarding/`) build the profile from a resume, a LinkedIn PDF export, a portfolio, links, pasted text or a guided interview. UI uploads are saved in `profile/entrada/`.
- Profile updates go through `src/onboarding/update.ts`: a proposal (`profile/atualizacao/proposta.json`, with the hash of the truth it was based on) that the user approves after seeing a line diff, then `rebuildBaseResumes` updates `base_resume.*.json` from the truth. New experiences must reach the base resumes, because the guards reject experiences missing from them. `ajf atualizar`, `ajf base --refazer` and Perfil → "Atualizar o perfil" in the UI are the entry points.
- The agent never reads or edits LinkedIn. `src/writers/linkedin.ts` writes plans and checks (`output/linkedin/plano_*` and `conferencia_*`) from the text or PDF export the user provides.
- Package folders live in `output/1-prontas-para-enviar`, `2-em-andamento`, `3-baixa-aderencia` or `4-encerradas` by status (`src/jobs/folders.ts`). Change status and paths through `jobs/store.ts#updateJob` (or `jobs/status.ts#changeStatus`), which moves the folder and keeps `outputDir`/`files` in `data/jobs.json` in sync.
- `examples/profile/` is a fictional profile used by the tests (`tests/setup.ts` sets `AJF_HOME=examples`).

## Rules that must never be broken

- `profile/profile_truth.md` and `profile/base_resume.*.json` are the only sources of facts about the candidate. Never invent employers, titles, dates, numbers, tools, certifications or results. A job requirement without evidence is a gap, not something to fill.
- `profile/rules.json → neverClaim` lists claims the guards reject, for example a language level above the declared one, or a course presented as a certification. Do not hardcode person-specific rules in `src/`.
- Never submit an application, send an email or change LinkedIn on the user's behalf. The agent prepares material; the user reviews and sends.
- Keep the section headings when editing or generating `profile_truth.md`. `src/profile.ts#NON_EVIDENCE_HEADING` drops sections whose heading mentions "Lacuna", "Regras de comunicação", "A confirmar" or "Nunca" from the evidence used by the guards.
- Nothing in `src/` may be specific to one person or one profession. Prompts, sources and labels must work for any field.
- Never open URLs or paths through a shell (`cmd /c start`, `sh -c`). Job links come from third-party sites; use `src/util/open.ts#openExternal`.
- The local UI must stay bound to 127.0.0.1 and behind the token cookie. Every user-supplied string rendered in `src/ui/public/` goes through `esc()`, external links must be `http(s)` and files are served only from `output/` via `/files/`.

## UX

- `ajf` with no args opens the local web UI (`src/ui/`): `server.ts` (127.0.0.1 only, token cookie, static files, SSE), `routes/` (jobs, profile/onboarding/LinkedIn, preferences), `tasks.ts` (one-at-a-time queue that captures terminal output as the task log) and a no-build page in `src/ui/public/` (ES modules in `js/`). Without a profile the UI opens on the onboarding wizard, which reuses `onboarding/index.ts#buildAndSaveProfile` like `ajf init`. `ajf menu` opens the terminal menu (`src/menu.ts`). Keep the UI and the menu offering the same actions.
- A pasted job without a link (referral, e-mail, WhatsApp) can be researched on the web before triage: `src/jobs/research.ts#researchJob` (UI paste switch, `ajf add --pesquisar`, `ajf pesquisar`). It appends a `## Pesquisa na web` block to the description (replaced on re-run by `withoutResearch`) and stores the verdict in `Job.research`. It also stores the company's mission and values (`Job.research.culture`), only from the official page and with its link: `officialCulture` drops anything not on the company or posting domain, a URL with the company's name, or its careers page on a recruiting platform. Record only what the search found; never invent postings, links, contacts or values.
- Application-form questions ("why do you want to work here?") are answered by `src/writers/answers.ts` (UI tab Perguntas, `ajf responder`, menu). Same rules as the resume: facts only from the profile and what the person says; numbers and `neverClaim` are checked. Answers live in `Job.answers` and `perguntas_e_respostas.md` in the package folder. The prompt also gets `jobFocus` (the package's `analysis.json`, the triage's proof and gaps, the mission and values). A question about the company (`isCompanyQuestion`, no AI) on a job without researched mission and values makes the route return `{ suggestResearch }`, so the UI (and `ajf responder`/menu) offers to research first or answer with the posting only (`skipResearch`, `--pesquisar`). The question can also come from a screenshot (`readQuestionsFromImage`: transcription only, no profile data; UI paste/drop/button via `POST /api/jobs/:id/answers/image`, `ajf responder --imagem`, or a dropped file path in the menu).
- `ajf auto` runs `src/auto.ts`: search, then triage, then tailor every job with triage score ≥ `AJF_MIN_TRIAGE_SCORE`, then the dashboard. Web search defaults to `preferences.webSearchByDefault`.
- Repeated jobs are caught in `jobs/store.ts#upsertJobs` by `src/jobs/dedupe.ts` (no LLM): same canonical link (`canonicalUrl`, which also feeds `jobId`), or same company, similar title at the same level and overlapping description text. A near-duplicate from a search is saved as `discarded` with `duplicateOf`; a pasted one is saved normally, only flagged. Same company plus the same title is enough when the text can't be compared (short, or a web-search summary, `page.ts#isWebSummary`) or when the other job was already handled (package, application, rejection). After every search `store.ts#flagHandledTwins` flags saved jobs that match a handled one, and `ajf auto` checks again before each package. Reopening, or "Não é a mesma vaga", sets `notDuplicate` so the job is never flagged again. Near-duplicates only count within `AJF_REPEAT_WINDOW_DAYS` (90) of the other job's application or save date, and not when the new one was posted 14+ days after it: outside that, it is a reopened job (`reopenedFrom`, shown as "vaga reaberta"). The same link is always the same job. Recalibrate the thresholds on real data before changing them, and keep the tests in `tests/search.test.ts` passing.
- `src/jobs/open.ts` checks whether a job still takes applications (`pageVerdict` is pure and tested). `tailorJob` checks first and throws `JobClosedError` unless `ignoreClosed`; `ajf auto` discards closed jobs and moves on to the next one. When unsure the verdict is `sem_confirmacao` and nothing is blocked. `ajf conferir`, the menu and the UI button check every job not yet sent.
- The `gupy` source reads the `__NEXT_DATA__` of the portal search page; it needs queries in Portuguese.
- Packages with a final rating below `AJF_MIN_RATING` (7) get status `low_fit`.
- The package README (LEIA-ME) includes how to apply, based on `JobAnalysis.applyChannel` (email, linkedin, plataforma, site, whatsapp).
- Each package also gets `rascunho_candidatura.eml` (`src/writers/emailDraft.ts`: the application e-mail with the PDFs attached and `X-Unsent: 1`, opened by the user's mail program; plus `gmailComposeUrl` for Gmail on the web) and `ficha_de_candidatura.md` (`src/writers/applicationSheet.ts`: form fields from the package resume, no LLM). The agent only writes and opens the draft; the user sends it. UI: E-mails and Ficha tabs; CLI: `ajf rascunho`, `ajf ficha`; menu: same actions.
- "Já me candidatei" stores the channel in `Job.appliedVia` (`jobs/status.ts#APPLY_CHANNELS`), preselected by `guessApplyVia`; `ajf enviei --via`.
- A resume in Portuguese never carries the English title in parentheses: `profile.ts#withoutTranslatedTitles` strips it (package, base resumes, sheet). The truth keeps the English name in a "Cargo em inglês:" line.
- No em/en dash as punctuation in anything a recruiter reads (it reads as AI text): the prompts forbid it and `util/text.ts#withoutDashes` / `profile.ts#withoutDashesResume` strip it without the LLM (titles get parentheses, text gets commas, e-mail subjects a hyphen). Date and number ranges get a plain hyphen, so no "—" or "–" is left (the PDF template joins dates with " - "). Applied to the package resume, base resumes (on load and save), the PDF render, the sheet, the cover letter, the e-mails and form answers.
- Job text from a page or a paste goes through `jobs/page.ts#cleanJobText`: it cuts the rest of the page ("Vagas semelhantes", "Similar jobs"...), drops UI lines (buttons, counters, menus, login) and the repeated header, keeps the "Pesquisa na web" block. Readers (triage, tailor, answers, research, UI) clean saved jobs too. LinkedIn job pages use the description block (`linkedinText`).
- `output/painel.html` is regenerated after every CLI command.
- The UI works from 320 px (phone) up: at 900 px and below the sidebar becomes a bottom bar, and its foot (palette, AI, language) is reached through **⋯ Mais**, which opens the palette. Long unbroken text (file names, e-mails, paths) wraps (`overflow-wrap: anywhere` on panels and dialogs). After touching the layout, check narrow widths in both languages.
- UI language (pt-BR, en): the Portuguese text is the key. Page: `t("...")` from `js/i18n.js` (loaded by `js/boot.js` before `main.js`; choice in localStorage `ajf.lang`). Server: `c.t(...)` in routes (task names and results) and `new HttpError(status, "Texto {x}", { x })`, translated in `src/ui/i18n.ts` by the `x-ajf-lang` header. Every new UI text gets its English entry in `src/ui/public/locales/en.json`; pass literals to `t()` (`cond ? t("a") : t("b")`) so `scripts/i18n.ts` finds them. `npm run i18n` lists missing or unused keys and `tests/i18n.test.ts` fails on them. Labels the server sends ready-made (`STATUS_LABELS`, `APPLY_CHANNELS`, source descriptions, provider labels) are translated on the page or in the route; dictionary values may hold simple HTML, outside values still go through `esc()`.

## Checks

- `npm run typecheck` and `npm test`. Tests are offline and cover guards, the refine loop, filter, ATS, rules, provider selection and CLI detection, JSON extraction, finding jobs by name, package folders by status, the UI parsers (pending items, e-mail sections), canonical links and repeated jobs, the closed-job verdict, the Gupy parsers, the e-mail draft (.eml), the application sheet, the English-title cleanup, the apply-channel guess, the job-page cleanup, the dash cleanup, the UI translation coverage (every UI text in `en.json`), company-question detection, official mission and values, the answer focus and image input (type by the first bytes, the request format of each AI, questions read from a screenshot).
- After touching `src/ui/public/js/`, run `node --check` on the changed files (they are not type-checked) and open the UI with `npm run demo` (fictional profile and jobs in `demo/`, no LLM; `scripts/demo.ts`).

## Docs

- `README.md` is the showcase, `docs/user-guide.md` the user guide (every screen, commands, FAQ) and `docs/how-it-works.md` the internals (pipeline, guards, providers, UI, code map). They are in English; the Brazilian Portuguese copies are `README.pt-BR.md`, `docs/guia-de-uso.md` and `docs/como-funciona.md` (also `CONTRIBUTING.pt-BR.md` and `SECURITY.pt-BR.md`). Every change goes to both languages, and each file links to the other at the top. In the English docs, buttons and screens use the English UI labels (`locales/en.json`); the Portuguese docs use the Portuguese ones.
- Update the user guide when something users see changes. Issue and PR templates in `.github/` are bilingual.
- Screenshots come only from `npm run demo`, never from real data: `docs/images/` with the UI in Portuguese for the Portuguese docs, `docs/images/en/` (same file names) with the UI in English for the English docs. The logo is `src/ui/public/logo.svg` (also the UI favicon).
- `npm run ajf -- base` renders the base resumes without calling the LLM. Run it after touching `src/render/`.
- `npm run ajf -- ia --testar` makes one short real call to the active provider.
